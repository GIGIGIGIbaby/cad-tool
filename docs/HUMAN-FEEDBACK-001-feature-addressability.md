# HUMAN-FEEDBACK-001：模型树只有冻结实体，人类无法编辑、无法寻址到孔/特征级

- 状态：**开放**（待产品决策）
- 来源：2026-10-13 履带驱动轮建模会话，人类用户在 FreeCAD 里实际查看模型后的反馈
- 影响面：建模方式（agent 侧）+ 桥接/观察设计（工具侧）
- 相关既有结论：[feedback.md](feedback.md) 第 8、9 条（FeaturePython 重开失效、脚本形状是冻结形状）

## 1. 人类原话（问题陈述）

> 模型树中只能够看到"履带驱动轮"这样一个实体，没有对应的草图和特征。我们是用代码直接
> 生成体块的，这和 FreeCAD 现有特征树结构的兼容性不足，不方便人类编辑。而且当我发现模型
> 某个地方不对时，我用语言没办法描述问题在哪里——我需要知道对应的编号，比如"哪个孔"是
> 第几号。我至少要能点一下查看它。但现在没有这些东西。

拆成两个独立问题：

1. **可编辑性**：模型树里只有一个 `Part::Feature` 冻结实体，没有草图/特征，人类在 FreeCAD
   里既看不懂建模意图，也无法手动改尺寸验证想法。
2. **可寻址性（feature addressability）**：人类想反馈"某个孔不对"，但孔/齿槽/面没有稳定
   编号，导致"我说的这个孔"和"agent 改的那个孔"之间没有共同语言。

## 2. 本次会话的复现场景

驱动轮模型里有 8 个螺栓孔 + 6 个减重孔 + 12 个齿槽。人类想说"某个孔的位置不对"时，今天
只有三种蹩脚表达方式，全都不可靠：

| 表达方式 | 问题 |
|---|---|
| 截图 + 时钟方位（"3 点钟方向那个孔"） | 依赖视图角度；换个视图就错位 |
| face index（如 Face107） | **实测不稳定**：重建后 OCCT 元素名重新生成，上次的 107 这次未必还是它 |
| 描述坐标（"x=58, y=0 那个孔"） | 人类不可能随口说出建模坐标 |

agent 侧同样尴尬：为了回答"是哪个孔"，我在会话里不得不临时写调试脚本（`debug_faces.py`）
去 dump 每个圆柱面的轴线、半径、序号——这份清单人类看不到，下次运行还会变。

## 3. 现状核对：桥接设计支持什么、不支持什么

| 能力 | 现状 | 证据 |
|---|---|---|
| 对象级观察 | ✅ `inspect` / `inspect --format code` 给对象、依赖、参数、几何汇总 | 本次 `inspect --format code` 只列出 1 个 `DriveSprocket` 对象 |
| 面/孔级寻址 | ❌ 无 | 快照头部自声明："Native Face/Edge element names are not guaranteed stable across geometry changes" |
| 特征级编号（"3 号孔"） | ❌ 无任何通道产出 | 观察、渲染、导出均无此概念 |
| 点选 → 查询 | ❌ 无 | 明确不做 GUI 桥接（feedback.md 第 5 节）；`ViewObject` 在无 GUI 时为 `None` |
| 渲染图上标注编号/尺寸 | ❌ 无 | render 元数据自声明"不是 GUI 截图、无选中态、无尺寸标注" |
| 模型树可编辑 | ⚠️ 取决于建模方式 | 工具允许任意原生 API 编排；本次用脚本布尔 + `Part::Feature`，所以树上没有特征 |

**结论：人类这种"指着某个几何说它不对"的输入，当前桥接设计不支持。**
注意最后一条的归因：模型树难看是 agent 的建模方式造成的（可以用原生特征树改善），
而寻址/点选/标注是工具能力缺口，两条线要分开治理。

## 4. 影响

1. **反馈回路断在最关键的一环**：现有通道（运行证据/状态观察/渲染/剖面）都能告诉人类
   "模型是什么"，但人类无法把"哪里不对"精确送回给 agent，只能靠文字描述 + agent 反复猜测。
2. **修改不可控**：人类说"改那个孔"，agent 重跑脚本后所有几何重建，face index 全变，
   无法确认"改的确实是那一个"，回归核对成本高。
3. **协作门槛被抬高**：人类必须学会用坐标/方位描述几何，这恰恰是 CAD 交互本该消掉的东西。

## 5. 需求（用户故事 + 验收标准）

**用户故事**：作为人类，我在 FreeCAD 里看模型时，能对任意孔/齿槽/面看到一个**稳定编号**，
我能直接说"3 号螺栓孔位置不对"，agent 能定位到同一编号的几何并修改，改完我还能在新版本里
找到对应的"3 号"。

验收标准（可测）：

1. 人类打开 FCStd，模型树呈现有意义的结构（特征/部件命名可读），关键尺寸可手动修改验证；
2. 存在一份机器可读、人类可查的**几何元素清单**（编号 ↔ 类型/轴线/半径/相位），编号跨重跑
   稳定（同参数重建 → 同编号；参数变化导致元素增删时编号规则可解释）；
3. `inspect`（或新增子命令）可按编号查询单个元素的全部度量；
4. 渲染图可选输出**带编号标注**的视图（或编号对照表 + 引线图），人类看图即可报号；
5. 全链路走通一次：人类报" N 号孔不对" → agent 定位 → 修改 → 新版本里 N 号孔可核对。

## 6. 可能的方向（讨论用，非承诺）

- **A. 建模方式：原生特征树**（解决可编辑性）
  用 `Sketch + Pad/Pocket`、PartDesign、`Spreadsheet + 表达式`重建驱动轮：每个孔一个命名特征
  （`BoltHole_03`），模型树可读可改。注意 feedback.md 第 8、9 条：工程模块的 FeaturePython
  重开失效，参数化必须用原生对象 + 表达式。齿形草图工作量大，需要取舍（齿形可以是单个
  命名特征，孔系逐个建特征）。
- **B. 观察侧：元素清单 + 稳定编号**（解决可寻址性，最小闭环）
  在观察层给孔/圆柱面/关键面生成语义候选清单：编号由**几何语义**派生（类型 + 轴线 + 半径 +
  相位角），不依赖 OCCT face index；支持按编号查询；元素增删时编号规则明确（如按角度排序
  重排 + 变更清单 diff）。这与 feedback.md 第 4.7 条一致：孔只能按轴线+半径+拓扑判**候选**，
  编号体系也应标注"候选"性质与判据。
- **C. 视觉侧：编号标注图**（解决"看图报号"）
  `render` 增加 `--labels` 一类的输出：编号引线标注在孔位旁（离屏 VTK 文本标注即可，不违反
  "不做 GUI 桥接"）。
- **D. GUI 点选辅助**（完整体验，但需产品决策）
  一个只读 FreeCAD 宏/面板：点面 → 显示稳定编号。它不违反"命令行不接管 GUI"（是用户主动
  运行的查看器），但引入了需要用户安装的组件，与"不装插件、不改用户偏好"的现行边界冲突，
  **需要先决策**。

推荐落地顺序：**B → C → A**（先让"报号—定位"闭环跑通，再解决模型树），D 单独决策。

## 7. 待决策问题

1. 稳定编号的生命周期：按几何语义派生 vs 显式命名清单（写进工程配置）？元素增删时是
   保号重排还是冻结已发放编号？
2. 编号是否要进 STEP/导出（外部协作也要能指认），还是只存在于工程内观察层？
3. "模型树可编辑"要不要立为建模规范（例如：交付模型必须是原生特征树），还是按任务取舍？
4. GUI 点选查看器做不做？
