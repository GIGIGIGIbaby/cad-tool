## Findings

1. **Inherited route** built every part from native parametric primitives (`Part::Box/Cylinder/Cut`) with spreadsheet expressions on dimensions and `Placement`. The saved file is genuinely parametric. Its own listed weaknesses (screw axial location and LM8UU retention not modelled, nut/rod over-constraint, 0.41 mm rod sag at S300) are the ones an engineer would raise.

2. **GPT-6 Sol** used project FeaturePython proxies. FreeCAD 1.1.3 blocks them on reopen: `PropertyPythonObject::Restore: blocked import of module 'stage_parts' during document restore. Only modules from FreeCAD or installed addons are permitted.` Only re-running `main.py` (which re-binds proxies) updates geometry. It reported this honestly. The carriage is a plate resting on rods with no bearings; coupling has no bores.

3. **DeepSeek Flash** cut the screw bores in coupler, nut block and both supports along **Y** (`cyl_y`) while the screw runs along **X** (`cyl_x`). The screw therefore passes through solid material, and each support is cut into two solids. The agent observed "wrong" `common()` volumes and split solids, **concluded the OCCT boolean was inaccurate**, replaced the check with a probe-point method, and reported zero interference. The render shows the split U-shaped supports, but this was not noticed. (Its early `PosX`-property attempt on a frozen `Part::Feature` was abandoned in favour of `Placement` expressions, which work after reopen.)

## Implications for V3

- `docs/feedback.md` §4.8 ("FeaturePython can be restored if the module is importable") is **false for FreeCAD 1.1.3 document restore**; it led a model down a dead end. Recommend native parametric objects + expressions for anything that must stay parametric after reopen.
- Add: script-generated `Part::Feature` shapes are frozen; spreadsheet changes only move them if `Placement` (or a native feature's properties) carries an expression.
- Add: when a boolean result looks "wrong", first check operand validity/solid count and axis/orientation of the tool bodies before suspecting the kernel.
- All three agents used correct standard dimensions (NEMA17, LM8UU, 608, T8 nut, MGN12); no evidence yet that the V2 parts catalogue needs porting.
- Render framing leaves ~50% whitespace; small parts are hard to see.

## Follow-up applied

- Docs: `feedback.md` §4.8 rewritten (+§4.9 frozen `Part::Feature`, §4.10 suspect inputs before the kernel); `SKILL.md` gained "native objects + expressions" and "see inside / interference" sections; `state-sketch.md` FeaturePython note corrected. Re-checked: pre-importing the project module before `openDocument` still leaves all 12 proxies `None`.
- Tool: `cad3 render --section AXIS=MM` (half-space sections, overlaps red + listed). On the Flash model, `--section y=58` shows the lead screw red through nut block, both supports and the coupler, and the cross-drilled nut bore as a circle. Views are now framed from projected bbox corners instead of the bounding sphere.

## Correction and round 2 (GPT-6 Sol rerun with the corrected skill)

**Probe bug found and fixed.** The first probe wrote plain numbers (`"200"`) into alias cells. When a model stores lengths with units (`"200 mm"`) and uses expressions like `Params.CarriagePos + 39 mm`, a plain number causes a unit mismatch and the dependent objects become Invalid. The probe now keeps the cell's unit. Re-judging all projects: inherited and GPT-6 Sol round 1 unchanged; **DeepSeek Flash's carriage does move correctly after reopen** — the earlier "nothing moves / Params Invalid" was the probe's fault. Its 4 real interferences stand.
